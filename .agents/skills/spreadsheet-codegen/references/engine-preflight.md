# 引擎预检：`engine: excel` 还是 `engine: snapshot`

**先定引擎，再写模板。** 引擎决定模板里能用哪些 Jinja 语法；反过来（先写模板再发现引擎不支持）
就只能整篇重写。

默认是 `engine: excel`（**公式模式**）：Output 表里写的是活公式，改参数 Excel 自己重算。
`snapshot` 是备选，只有在公式模式**确实表达不了**的时候才用，而且必须显式声明。

---

## 1. 支持矩阵

### 公式模式收得下的

| 写法 | 编译成 |
| --- | --- |
| 字面文本 | 原样（拼进公式字符串） |
| `{{ x }}` | `Prefix & Value & Suffix`（与快照模式逐字一致） |
| `{{ x.value }}` / `{{ x.text }}` | 取值列的纯值 |
| `{{ x.prefix }}` / `{{ x.suffix }}` | 前缀 / 后缀列（绝对引用，**不随 Case 变**） |
| `{{ case_name }}` | 该 Case 的 Local 表表头（相对列 / 锁死行） |
| `{{ template_name }}` | 常量 |
| `{# 注释 #}` | 整段丢掉 |
| 同一行内闭合的 `{% if %}…{% endif %}` | Excel 嵌套 `IF(...)` |

### 公式模式收不下的（写了就在 `init` / `render` / `validate` 阶段报错，并带行号）

| 写法 | 为什么 |
| --- | --- |
| `{% for %}` / `{% set %}` | 循环与赋值会改变"一个 Case 占几行"，而公式模式是**一行模板 → 一个单元格** |
| **跨行**的 `{% if %}` | 同上 |
| `{% include %}` | 片段让行数不可预测 |
| 任何**过滤器**：`{{ x \| upper }}`、`{{ x.value \| pvs("P","S") }}` | 单元格引用表达不了 |
| 任何**表达式 / 运算**：`{{ baud + 1 }}`、`{{ x.value * 2 }}` | 同上 |
| `{{ x.name }}`（除 `.value`/`.text`/`.prefix`/`.suffix` 之外的属性） | 只有这四种有对应的列 |
| 引用 YAML 里**没定义**的变量 | 公式需要知道它落在 Global 还是 Local 表 |

报错长这样，会直接告诉你怎么办：

```text
ERROR 公式模式不支持 {% for %}：模板 'x' 第 3 行 …请把该模板改回 engine: snapshot
```

## 2. 头号误判：目标语言自己的控制流不是 Jinja 控制流

这是实测里反复出现、代价最大的一处误判（`abs_fpi/FINDINGS.md` 专门更正过）：

> **生成目标语言里的 `if / else / { } / for` 只是字面文本，公式模式照收不误。
> 真正拦住公式模式的是 *Jinja* 的 `{% %}` 与 `{{ | 过滤器 }}`。**

GeniE 的 JavaScript 函数体里大段 `if (...) { } else { }`、C 里的 `switch`、NASTRAN 的语句，
都只是**要原样输出的字符串**，跟公式模式毫无冲突。看到目标代码里有分支就退回 `snapshot`，
等于白白丢掉这个工具的核心价值。

**先按公式模式写。** 只有在真的用到 Jinja 的循环 / 过滤器 / 跨行分支时才降级。

> 一个正面的样板思路：`abs_fpi` 里本来想用 Jinja 的 `{% if %}` 做坐标映射，最后改成
> **6 个纯替换变量**（`neg_x` 填 `-` 或空、`ax_x` 填 `1/2/3`），整份模板因此能进公式模式。
> 遇到"想写 Jinja 分支"时，先问一句：**这些差异能不能变成参数**？

## 3. 条件（`{% if %}`）的规矩

### 3.1 必须整段写在同一行内

```jinja
y = {% if flag.value == 1 %}{{ L }}{% else %}- {{ L }}{% endif %};
```

### 3.2 条件里的变量必须带属性，不能裸写

```jinja
{% if draft.value > 20 %}…{% endif %}      ✅
{% if kind.value == "EXT" %}…{% endif %}   ✅
{% if not flag.value %}…{% endif %}        ✅
{% if draft > 20 %}…{% endif %}            ❌ 报错：请写 draft.value
```

这不是洁癖：快照模式里裸变量是 `VarValue` **对象**，`VarValue > 20` 直接抛 `TypeError`；
而 `.value` 在两种引擎里都是"纯值"—— **只有这种写法能让两边逐字一致**。
规则与 `case_filter`、`asserts` 相同。

**例外**：`case_name` / `template_name` 可以裸写（它们没有 `.value`）。

### 3.3 支持的条件写法

| 类别 | 写法 |
| --- | --- |
| 比较 | `==` `!=` `<` `>` `<=` `>=` |
| 逻辑 | `and` / `or` / `not`（可加括号） |
| 真假判断 | `{% if flag.value %}` —— 数值比 `0`，文本比空串 |

`{% elif %}` 是**无损**降级（等价于 `else` 里再套 `if`），所以三段分支不必退回快照模式：

```jinja
{% if kind.value == "EXT" %}E{% elif kind.value == "INT" %}I{% else %}X{% endif %}
→ IF(<kind="EXT">,"E",IF(<kind="INT">,"I","X"))
```

## 4. 公式模式的四条成本

### 4.1 值只活在 Excel 里

`openpyxl` 只写公式、不算公式。所以：

- `--outdir` 导出的代码文件**仍由 Python 渲染**（模板是纯替换，内容与公式等价）；
- "改参数自动同步导出文件"**做不到** —— 要再跑一次 `render --outdir`；
- `check` 默认把 Output 表的公式**在 Python 里求值一遍**再与 Python 渲染逐行比对
  （另有一套独立的求值器），所以"公式算出来的对不对"是有证据的，不用自己核对。
  参数单元格本身是手写公式（如 `=L/10`）时离线读不到值，会降级成"只比公式"并给出提示；
  `--no-values` 可显式关掉。

### 4.2 改什么要重跑 `--write-excel`

| 动作 | 要重跑吗 | 为什么 |
| --- | --- | --- |
| 改 Global / Local 的**参数值** | ❌ 不用 | 公式引用单元格，Excel 打开即重算 |
| 插 / 删**变量行** | ❌ 不用 | `INDEX/MATCH` **按变量名**定位 |
| 改变量行的**前缀 / 后缀**（C / D 列） | ❌ 不用 | 同上 |
| **增 / 删 / 移动 Case 列（行）** | ✅ **要** | 值列用**相对列**（`E:E`）→ 列一移位就指错工况 |
| 改 **YAML**（模板 / 变量 / 引擎） | ✅ **要** | 公式是写进格子的文本 |
| 改 `case_filter` / 新增 Case 表头 | ✅ **要** | 归属与列顺序变了 |

增删 Case 列这件事工具**能发现**：`check` 会报 `value_mismatch`，提示"结构改过？请重跑"。

### 4.3 公式有长度成本

- 一个 `{{ x }}` 大约 **300–500 字符**（`INDEX` + `MATCH` + `ISBLANK` + 回落 + 前后缀）。
- 经验值：**一行 8 个以上占位符就该考虑拆行**（约 3000 字符），`validate` / `render` 会告警。
- 单格**硬上限 8192 字符**，超过直接报错。
- 实测样例：`abs_fpi` 汇总表里一行 6 个占位符 → 单格 2702 字符。

### 4.4 两个已知差异

| 差异 | 说明 | 规避 |
| --- | --- | --- |
| `type: bool` | Excel 里是 `TRUE` / `FALSE`，Python 侧是 `true` / `false` | **bool 变量建议用 `type: string`**，或该模板用 `snapshot` |
| 区域设置 | 欧洲区域小数点是 `,`，会让数值形态与 Python 侧分叉 | 换区域前先验一遍 |

> 数值形态本身已经对齐：两边都按 **15 位有效数字**（Python 侧 `%.15g`、Excel 侧隐式转换），
> `340.0` 两边都输出 `340`。这条是刻意做的，**不是**用 `TEXT()` 拼的。

## 5. 什么时候真的该用 `snapshot`

只在下面这些情况下，才给模板显式写 `engine: snapshot`：

1. 模板里有**跨行**的 Jinja 控制流（`{% for %}`、跨行 `{% if %}` / `{% set %}`）；
2. 模板里用了**过滤器**（`upper` / `format` / `round` / `join` …）；
3. 模板里用了 `{% include %}` 片段；
4. 需要 `type: bool` 与 Python 完全一致的文本形态；
5. 目标区域的小数点不是 `.`，且模板里数值形态敏感。

代价要说清楚：**快照模式下输出表是文本快照，改了参数必须重跑 `render --write-excel`**，
工作簿不再独立可用。所以能留在公式模式就留在公式模式。

两种引擎可以**在同一个 YAML 里共存**（逐模板声明），一个工作簿里有的表是公式、有的是快照。

## 6. 派生参数（`derived:`）与公式模式

`derived:` 让参数引用参数（同 Case 的 local + global），**它也支持公式模式**：能翻译的表达式
会写成 Excel 公式，改输入自动重算。

| 能翻译 | Excel |
| --- | --- |
| `min` / `max` / `abs` / `int` / `float` / `len` / `x \| string` | `MIN` / `MAX` / `ABS` / `TRUNC` / 原值 / `LEN` / 原值 |
| `+ - * / ** %` | `+ - * / ^ MOD` |
| `~`（字符串拼接） | `&` —— **不要用 `+` 拼字符串**，Excel 的 `+` 不做文本拼接 |
| `a if cond else b` | `IF(cond,a,b)` |
| 比较、`and/or/not`（只在条件里） | `= <> > < >= <=` |

**不翻译**的（`round` / `ceil` / `floor` / `//` / `upper` / `lower` / `sum` …）：不是报错，而是
**降级成"把 Python 算好的值写进格子"并告警**，此时改输入要重跑 `--write-excel`。
`round` 之所以不翻译是因为 Python 用**银行家舍入**（`round(2.5) == 2`）而 Excel `ROUND` 是四舍五入。

约束：`derived` 只能引用 `global` 与**同一个 Case** 的 `local`（global 不能引用 local）；
不能给派生参数加取值约束；派生参数**不能**用在成员表里。

## 7. 一条被旧文档带偏的经验（已实测更正）

老资料（`abs_fpi/TEMPLATES.md` §4，0.3.0 时代）写着"公式模式下 `case_filter` 的工况**必须相邻**"。
**这条在 0.11.0 已经不成立**，实测：

```
Local 表 Case 列：  E=EXT-A   F=INT-A   G=EXT-B     ← INT 夹在中间
Code EXT 表写出的公式：
  B2 → 'Local Parameter'!E$1 & …INDEX('Local Parameter'!E:E, …)   ← 对 EXT-A
  C2 → 'Local Parameter'!G$1 & …INDEX('Local Parameter'!G:G, …)   ← 对 EXT-B（跳到 G）
check → OK 输出表与当前参数一致
```

原因是引用用的是**真实的 Case 轴**，不是输出列序号，所以中间隔着别的规则集也不会指错。
**别再为了"必须相邻"去重排用户的工况。**

> 仍然成立的一条：**手加 Case 列时要先把归属变量（`case_filter` 用的那个，如 `kind`）填上**。
> 留空会回落 YAML `default`，这一列就**悄悄进了某个规则集**；`render` / `check` 会对
> "整列都空的 Case"给提示。给 `kind` 加 `choices` 就能把这类错误变成硬报错。
